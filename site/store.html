Store and SyncEngine

SyncEngine is the client half of a modx-core app: it loads the data once, follows the server’s change stream, shows writes at once, and keeps the ones it could not send — across reloads — until the network is back.

The loop

  1. Bootstrap. GET bootstrapPath → { seq, todos: [...] }: one table per collection, at sequence seq.
  2. Live. An SSE stream (eventsPath). On every (re)connection it first asks changesPath(seq) for what it missed; changes are applied once each, by seq. A 410 (or event: reset) means “too far behind”: bootstrap again.
  3. Writes. create / update / remove change what the UI sees immediately (base + pending writes) and go out one at a time. A 4xx rolls the write back; a network error keeps it queued.
import { createHttpTransport, localStorageSync, SyncEngine } from '@saidmashhud/modx-store';

interface Model { todos: { id: string; title: string; done: boolean } }

const sync = new SyncEngine<Model>({
  transport: createHttpTransport(),
  collections: ['todos'],
  bootstrapPath: '/api/bootstrap',
  changesPath: (since) => `/api/changes?since=${since}`,
  eventsPath: '/api/events',
  owner: session.userId,                                  // whose data this is
  storage: localStorageSync('todos', { owner: session.userId }),
  endpoints: { todos: {
    create: (row) => ({ method: 'POST', path: '/api/todos', body: row }),
    update: (id, patch) => ({ method: 'PUT', path: `/api/todos/${id}`, body: patch }),
    remove: (id) => ({ method: 'DELETE', path: `/api/todos/${id}` }),
  } },
});

await sync.start();
sync.select((t) => Object.values(t.todos)).subscribe(render);
const id = sync.create('todos', { title: 'Buy milk', done: false });  // on screen now, temporary id
sync.update('todos', id, { done: true });                             // follows the real id later

Offline queue

Pending writes, the base tables and seq are saved through a SyncStorage after every change (saveDebounceMs coalesces). On the next start() they are loaded back and the queue is sent. Browser offline / online events update status$ and reconnect at once instead of waiting out the backoff.

  • localStorageSync(key) for most apps; memoryStorage() in tests; your own { load, save } for IndexedDB.
  • Temporary ids are replaced by the server’s — also inside writes still waiting in the queue.
  • Several tabs: localStorageSync merges on every save with what another tab stored (union of both queues, minus writes either tab finished).

Idempotency: a retry is applied once

When a write’s answer is lost (the connection drops after the server committed), the client cannot know whether it landed. So every write carries Idempotency-Key: <opId> — the same value on every retry and after a reload, because the opId is stored with the queue. A server that keeps keys (modx-core idem.h) answers a repeat from its record instead of applying it twice.

new SyncEngine({
  // …
  idempotency: { header: 'Idempotency-Key', key: (w) => w.opId },  // the default
  opId: () => `op_${crypto.randomUUID()}`,                           // unique per account, across tabs and devices
});

Pass idempotency: false to send no header. Keys must be 1–128 printable ASCII characters.

Owner scoping

Stored data outlives a session: a sign-out, or another account on the same browser, must not send the previous person’s queued writes. Set owner (a user id, or user@workspace) and pass the same value to localStorageSync. A stored snapshot of another owner — or of another schemaVersion — is not hydrated: its writes are dropped, never sent, and reported.

sync.discarded$.subscribe(({ reason, pending }) => {
  if (pending.length) toast(`${pending.length} unsent changes from a previous session were discarded (${reason}).`);
});

Bump schemaVersion when stored rows or pending writes change shape.

Retries

FailureWhat happens
Network errorThe write stays queued and is retried with backoff (retryDelay, default exponential with jitter, capped at 15 s) — forever, it is the offline case.
5xx, 408, 429Retried with backoff up to maxRetries (default 8, DEFAULT_MAX_RETRIES), then rejected: rolled back, reported on rejected$, and the writes behind it go out.
Other 4xxRejected at once: rolled back together with writes that depended on a row it was creating; reported on rejected$.
4xx on bootstrap or the reconnect probeAccess is gone: the engine stops, lost$ fires, status 'error' (needs probe: true for the stream).
 
sync.rejected$.subscribe(({ write, error }) => toast(`Could not save: ${error.message}`));
sync.status$.subscribe((s) => banner(s === 'offline' ? 'Offline — changes will be sent later' : ''));

Storage errors

A save that throws or rejects (quota exceeded, Safari private mode, a blocked IndexedDB) is reported on storageError$, not swallowed. The queue then lives in memory only until a later save succeeds — a reload now would lose it, so tell the person.

sync.storageError$.subscribe(() => banner('This browser is not keeping offline changes. Stay on the page until they are sent.'));
// or handle it in the storage itself:
localStorageSync('todos', { owner, onError: (e) => report(e) });

The rest of the package

  • Store: Redux-style on RxJS, effects as (actions$, state$) => actions$, memoized select, createSelector.
  • Tables: immutable id → row maps (putOne, patchOne, removeOne), so reference equality drives memoization.
  • Query: filterBy, sortBy, groupBy, fuzzy search, sortOrderBetween for drag and drop.
  • Router: createRouter({ item: '/lists/:list/items/:id' }), and UiRouter with route$ on the History API.
  • OT: plain-text operational transformation (transform, compose, invert, OtClient), the counterpart of modx-core’s ot.h.

In the UI, bind any of these streams to an element with ObserveController — the UI package does not depend on rxjs.
